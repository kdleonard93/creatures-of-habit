# Database Layer Audit: Creatures of Habit

Scope: this report audits the persistence layer of Creatures of Habit on branch `task/audit-updates`: the Drizzle schema (`src/lib/server/db/schema.ts`), the driver wiring (`src/lib/server/db/index.ts`), every SQL file in `migrations/` with its `migrations/meta/` snapshots and journal, and every server file that reads or writes the database (`src/lib/utils/dailyHabitTracker.ts`, `src/lib/server/services/**`, `src/lib/server/auth.ts`, and the route handlers under `src/routes/`). It covers schema-versus-migration drift, missing constraints and integrity gaps, data lifecycle and safety, and query-level performance and transaction behavior. Findings reuse backlog IDs D-1..D-3 where they match and add D-4 and beyond. Evidence is code-level unless stated otherwise; live Turso state is called out as unverified. A local reproduction was run with the installed `@libsql/client` 0.14.0 and `drizzle-orm` 0.36.4 to ground the foreign-key and transaction claims.

Severity counts: critical 0, high 3 (D-1, D-2, D-4), medium 5 (D-3, D-5, D-7, D-9, D-10), low 2 (D-6, D-8).

### D-1 Migration and snapshot drift on quest indexes, and the journal tag mismatch

Severity: high
Status: open
Evidence: `src/lib/server/db/schema.ts:214` declares `unique_question_answer` on `quest_answers`; `migrations/0021_noisy_gravity.sql:2` creates `unique_quest_question_answer`; `migrations/0022_quest_answer_uniqueness.sql:3` creates `unique_quest_answer_per_question` with `IF NOT EXISTS`; `migrations/0025_oval_dark_phoenix.sql:2` creates `unique_question_answer`. `schema.ts:193` declares only a non-unique `idx_quest_questions_instance`, while `migrations/0021_noisy_gravity.sql:3` creates `unique_quest_question_number` and `0022_quest_answer_uniqueness.sql:6` creates `unique_quest_question_number_per_instance`. Snapshots diverge: `migrations/meta/0021_snapshot.json:1049,1340` contain `unique_quest_question_answer` and `unique_quest_question_number`; `migrations/meta/0022_snapshot.json:1041-1048,1323-1331` contain neither; `migrations/meta/0028_snapshot.json:1123` has `unique_question_answer` and `:1413-1421` has only the non-unique `quest_questions` index. `migrations/meta/_journal.json:160-165` lists entry idx 22 as `0022_foamy_lord_hawal`, but the file on disk is `0022_quest_answer_uniqueness.sql`; git history shows `0022_foamy_lord_hawal.sql` contained `DROP INDEX` for the two 0021 uniques and was deleted in commit `7742f2e` without updating the journal. `migrations/0024_slippery_tomas.sql:1` drops `idx_user_waitlist_email`, which was never created (0023 created `user_waitlist_email_unique`), a no-op that signals hand-editing.
Impact: the uniqueness state of `quest_answers` and `quest_questions` is different in `schema.ts`, in each snapshot, and in the live database. SQLite `IF NOT EXISTS` matches on index name, not column set, so on a database that applied 0021 then the hand-written 0022 then 0025, all three `(quest_instance_id, question_id)` uniques coexist and both `(quest_instance_id, question_number)` uniques coexist. The journal tag points at a deleted file, so `drizzle-kit migrate` cannot resolve the 0022 step and fresh-database replay is broken. What the tools would do: `drizzle-kit generate` diffs `schema.ts` against the last snapshot (0028), which already matches, so it emits nothing and the drift never self-heals. `drizzle-kit push` introspects the live database instead and would propose dropping the live-only indexes (both `quest_questions` uniques and the extra `quest_answers` uniques) and rebuilding `quest_answers` to change its foreign keys. Both outcomes are risky: generate is silently blind, and push is destructive and could remove the only guard against duplicate question numbers.
Proposed fix: reconcile in a single forward, hand-reviewed migration. Pick one canonical name per constraint (`unique_question_answer`, and a `quest_questions(quest_instance_id, question_number)` unique), add them to `schema.ts` and the snapshots, drop the redundant live names, and regenerate `migrations/meta/_journal.json` entry 22 to point at a real file (or add `0022_foamy_lord_hawal.sql` back and make it a no-op). Run `pnpm db:check` to confirm journal and snapshot alignment. Do not use `push` against production.
Decision needed: `open-questions.md` (ownership of migration tooling). Cross-reference backlog S-3.

### D-2 Uniqueness enforced only in application code

Severity: high
Status: open
Evidence: `habit_completion` has no `(habit_id, completed_at)` unique; the route reads then inserts (`src/routes/api/habits/[id]/complete/+server.ts:36-46` then `:59-68`). `quest_instances` has no unique on user plus day; `getDailyQuest` reads then inserts (`src/lib/server/services/questService.ts:30-48` then `:68-83`). `habit_streak` has no unique on `habit_id`, and the update targets every row with that habit (`complete/+server.ts:73-81`). `creature.user_id` has no unique (`schema.ts:18-20`), yet loaders take `rows[0]` and the completion route updates every creature for the user (`complete/+server.ts:83-99`). `creature_equipment` has no `(creature_id, slot)` unique (`schema.ts:48-56`). Note that `creature_stats.creature_id` is unique (`schema.ts:33-36`), so that one is covered. `habit.category_id` is nullable and stored without ownership verification (`src/routes/api/habits/+server.ts:92`), and `habit.frequency_id` is nullable with daily habits storing null (`habits/+server.ts:65-84`).
Impact: concurrent or repeated requests can create duplicate daily completions, duplicate quests for the same user and day, duplicate streak rows, multiple creatures per user, and multiple items in one equipment slot. Duplicate streak or creature rows cause multi-row updates and wrong XP. A client can store a `categoryId` belonging to another user, because there is no foreign-key ownership rule and no check.
Proposed fix: add database-level uniqueness where semantics demand it: `unique(habit_completion.habit_id, habit_completion.completed_at)`, `unique(quest_instances.user_id, date(created_at))` via a generated day column, `unique(habit_streak.habit_id)` (or `(habit_id, user_id)`), `unique(creature.user_id)`, and `unique(creature_equipment.creature_id, slot)`. Validate `categoryId` ownership in the handler and consider making `frequency_id` non-null with an explicit daily row. Handle the resulting unique-constraint errors in the routes so a duplicate returns a clean 400 instead of a 500.
Decision needed: confirm per-habit versus global streak scope, and the weekly weekday model, in `open-questions.md`. Cross-reference backlog D-2.

### D-3 No defined Turso snapshot and rollback procedure before migrating

Severity: medium
Status: needs-decision
Evidence: `drizzle.config.ts:1-16` points writable tooling directly at `TURSO_DATABASE_URL` with no branch or backup step. Package scripts expose `db:push`, `db:generate`, and `db:migrate` against that same URL (`package.json:17-24`). There is no CI or script that snapshots before applying. The migrations include table-recreate patterns (`migrations/0011_noisy_lady_vermin.sql`) and would do more under `push`.
Impact: a botched or destructive migration has no tested rollback path. `push` can rebuild tables (create-copy-drop-rename), and a partially applied hand-edited migration leaves the journal and snapshots inconsistent with the live schema, as in D-1. Soft-deleted habit data is recoverable only while rows exist; hard delete via `/api/habits/[id]/permanent-delete` plus FK cascade is irreversible.
Proposed fix: define and rehearse this procedure before any migration. All command names should be verified against the installed `turso` CLI version, since subcommands have changed over time.
1. Capture a logical backup: `turso db dump <db> > backup-<date>.sql` (or `turso db shell <db> ".dump"`). Verify the file is non-empty and contains every expected table.
2. Create a restorable fork for fast rollback: `turso db create <db>-backup-<date> --from-db <db>`. Keep it until the migration is verified in production.
3. Rehearse on a staging fork: `turso db create <db>-staging --from-db <db>`, point a staging environment at it, and run migrations there first.
4. Apply to production with `pnpm db:migrate` only, never `pnpm db:push`.
5. Rollback: repoint `TURSO_DATABASE_URL` at the backup fork, or restore into a fresh database with `turso db shell <new-db> < backup-<date>.sql`.
6. Confirm final state with `turso db shell <db> ".indexes"` and the `__drizzle_migrations` table.
Decision needed: `open-questions.md` (backup retention and who owns production migrations). Cross-reference backlog D-3 and R-1.

### D-4 `quest_answers` foreign keys from migration 0020 lack `ON DELETE CASCADE`

Severity: high
Status: open
Evidence: `migrations/0020_curious_charles_xavier.sql:50-51` adds the columns as `ALTER TABLE quest_answers ADD quest_instance_id text NOT NULL REFERENCES quest_instances(id)` and `ADD question_id text NOT NULL REFERENCES quest_questions(id)`, with no `ON DELETE` clause, which is `NO ACTION`. `schema.ts:199-204` and `migrations/meta/0028_snapshot.json:1132-1158` both declare `onDelete: "cascade"`. A local reproduction with the app driver (foreign keys enabled, see D-5) showed that deleting a referenced parent row under this `NO ACTION` foreign key fails with `SQLITE_CONSTRAINT_FOREIGNKEY`.
Impact: the live table does not cascade the way the schema claims. Deleting a `quest_questions` or `quest_instances` row while answers exist raises a constraint error instead of removing the answers. `resetDailyQuest` happens to delete answers, then questions, then instances in the right order (`questService.ts:488-498`), which masks the problem today, but any other delete, including a future template or cleanup path, will fail or leave the intent unreachable. Because SQLite cannot alter a foreign key in place, correcting this requires a table rebuild.
Proposed fix: add a forward migration that rebuilds `quest_answers` with `ON DELETE CASCADE` on both keys, backfilling nothing (the columns are already present), and verify with an integration test that deletes a quest instance and asserts answers are gone. Do this only after the D-3 backup is in place.
Decision needed: none beyond sequencing after D-3.

### D-5 Foreign key enforcement is not explicitly enabled and relies on driver defaults

Severity: medium
Status: verify
Evidence: no `PRAGMA foreign_keys` or `foreign_keys` reference exists anywhere under `src/` (grep returns no matches). `src/lib/server/db/index.ts:18-20` creates the client and calls `drizzle(client, { schema })` with no pragma. A local reproduction with `@libsql/client` 0.14.0 against a `file:` database returned `PRAGMA foreign_keys = 1` and enforced a cascade, so the native libsql default appears to be ON. The remote Turso path uses the Hrana protocol (`node_modules/@libsql/client/lib-esm/hrana.js`), which was not exercised here.
Impact: if foreign keys are OFF on a given connection (some SQLite configurations, or a Turso setting change), every declared cascade silently becomes a no-op and deletes leave orphan rows, and the `NO ACTION` keys in D-4 stop failing. Because enforcement is implicit, behavior can differ between local dev (`file:local.db`) and production (Turso) with no code change. This is worse than either always-on or always-off because it is invisible.
Proposed fix: explicitly run `PRAGMA foreign_keys = ON` once per connection at client creation in `db/index.ts`, and verify the effective value on Turso with a one-off query. Add an integration test that asserts a cascade actually fires. If Turso cannot enable it, document that and enforce referential integrity in application code instead.
Decision needed: verify the production pragma value, then decide whether to enforce in the database or the application.

### D-6 Redundant indexes on `daily_habit_tracker`

Severity: low
Status: open
Evidence: `schema.ts:294-309` declares `idx_daily_tracker_user_habit_date` (non-unique) on `(user_id, habit_id, date)` and `unique_user_habit_date` (unique) on the identical column set, plus `idx_daily_tracker_user_date(user_id, date)`, which is a prefix of the unique index. The migration mirrors this at `migrations/0017_previous_naoko.sql:1-5`.
Impact: three indexes where one (the unique) plus one narrow index would suffice. Extra write cost and storage on every tracker insert or update, which happens for every active habit on dashboard load.
Proposed fix: drop `idx_daily_tracker_user_habit_date`; keep the unique constraint and either keep or drop `idx_daily_tracker_user_date` depending on the `(user_id, date)` query plan. Confirm query plans before dropping.
Decision needed: none.

### D-7 Timestamp representation is mixed between SQLite and ISO strings

Severity: medium
Status: open
Evidence: DB defaults use `CURRENT_TIMESTAMP`, producing `YYYY-MM-DD HH:MM:SS` in UTC (`schema.ts:11` and every `created_at`/`updated_at`). Several code paths instead write `new Date().toISOString()` with a `T` and a trailing `Z`: `quest_instances.activated_at` and `completed_at` (`questService.ts:140,343`), `habit.updated_at` (`src/routes/api/habits/[id]/+server.ts:53,98,127`), and `user.email_verified_at` (`src/lib/server/auth.ts:215`). `formatSqliteTimestamp` in `src/lib/utils/date.ts:14-16` writes the space-separated form. `dashboard/+page.server.ts:95-100` selects the latest completion with `MAX(completed_at)` and later code compares date strings lexicographically.
Impact: the same logical column holds two formats. Lexicographic ordering and `MAX(completed_at)` subqueries can order the two formats inconsistently (space `0x20` sorts before `T` `0x54`), so "latest completion" and any date-range comparison can be wrong. All values are UTC, so local-time users also see date-boundary off-by-one behavior.
Proposed fix: standardize on one representation, preferably the space-separated SQLite form everywhere via a single helper, and normalize existing rows in a data migration. Add a test asserting the chosen format and a `MAX` ordering test over mixed historical values.
Decision needed: confirm the canonical timestamp format, then cross-reference the timezone policy in `open-questions.md`.

### D-8 Boolean representation is inconsistent

Severity: low
Status: open
Evidence: most 0/1 columns use Drizzle boolean mode, for example `user.email_verified` (`schema.ts:12`), `habit.is_active` and `is_archived` (`schema.ts:93-94`), and `daily_habit_tracker.completed` (`schema.ts:291`). `user_preferences` declares its flags as plain integers (`schema.ts:259-267`), and the code compares them to `1` explicitly (`src/lib/server/services/notificationService.ts:93-99`). Settings writes them as `1`/`0` (`src/routes/settings/+page.server.ts:77-79`).
Impact: mixed typing is a recurring source of coercion bugs and confusion; `true`/`false` returned as numbers and compared with strict equality works only because the code is careful. The schema and snapshot show no database `CHECK` constraint on any of these columns, so any integer is accepted.
Proposed fix: convert `user_preferences` flags to boolean mode for consistency, or document the deliberate exception. Add `CHECK` constraints or a shared 0/1 domain if the database should enforce it. Low priority because behavior is currently correct.
Decision needed: none.

### D-9 Missing indexes for hot queries and one index-defeating predicate

Severity: medium
Status: open
Evidence: none of the following have an index: `habit_completion` (filtered by `user_id`, `habit_id`, `completed_at` in `dashboard/+page.server.ts:70-101` and `habits/+page.server.ts:43-62`), `habit` on `user_id`/`is_archived` (queried on every list and completion), `creature` on `user_id` (queried on nearly every request), `habit_streak` on `habit_id`, `habit_category` on `user_id`, `session` on `user_id`, and both token tables on `user_id` (`auth.ts:107,127`). `dashboard/+page.server.ts:86-101` runs a correlated `SELECT MAX(completed_at) ... WHERE habit_id = ?` per habit, which scans `habit_completion` each time. `getDailyQuest` filters with `date(createdAt) = today` (`questService.ts:36-37`), a function on the column that defeats the `idx_quest_instances_user_created` index defined at `schema.ts:170`. `waitlist/thank-you/+page.server.ts:8` runs an unindexed `count(*)` on `user_waitlist`.
Impact: full table scans on the busiest paths as data grows: dashboard and habits loads, every completion, and every auth session check. The quest lookup pays a function-evaluation scan despite having a purpose-built index.
Proposed fix: add indexes `habit_completion(user_id, completed_at)`, `habit_completion(habit_id, completed_at)`, `habit(user_id, is_archived)`, `creature(user_id)`, `habit_streak(habit_id)`, `habit_category(user_id)`, `session(user_id)`, and `user_id` indexes on both token tables. Rewrite the daily-quest lookup to compare a stored day column or a range on `created_at` so the existing index is usable. Confirm plans with `EXPLAIN QUERY PLAN`.
Decision needed: none.

### D-10 Unsafe transaction usage and multi-step writes without transactions

Severity: medium
Status: verify
Evidence: `src/lib/utils/dailyHabitTracker.ts:82-100` runs `Promise.all([tx.select(...), tx.select(...)])` inside a `db.transaction`. The drizzle libsql driver forwards concurrent statements to one `@libsql/client` transaction (`node_modules/drizzle-orm/libsql/session.js:54-72`), whose Hrana implementation guards transaction start with a single `#started` field (`node_modules/@libsql/client/lib-esm/hrana.js:27-64`), a pattern that is not designed for concurrent first statements. A local native-file reproduction of concurrent executes on one transaction passed, so this is a latent portability race, not a confirmed failure. Separately, several write sequences have no transaction: habit create inserts a frequency, a habit, and a streak row as three statements (`src/routes/api/habits/+server.ts:67-106`); the completion route checks, inserts, updates streak, updates creature, and marks the tracker across five statements (`complete/+server.ts:36-102`); `answerQuestion` inserts an answer, updates progress, and may complete the quest with no transaction and no optimistic lock, so two concurrent answers can lose an update (`questService.ts:178-318`); `spendStatBoostPoints` reads then updates (`questService.ts:395-461`).
Impact: a failure between steps leaves partial state (a habit with no streak row, a completion with no XP). Concurrent quest answers can corrupt `current_question`, `correct_answers`, or `stat_checks_passed`. The `Promise.all` inside the transaction is a latent risk if the app moves fully to remote Turso, where concurrent statements on one transaction are not guaranteed.
Proposed fix: replace `Promise.all` inside the transaction with sequential `await`s. Wrap each multi-step write in `db.transaction` and use conditional updates (`WHERE current_question = ?`) or a version column for the quest progress to make concurrent answers safe. Add integration tests that exercise concurrent completions and answers against a real libsql database.
Decision needed: decide the concurrency model for quest progress (optimistic lock versus serialized writes).

## Uncertainty

- Live Turso state is not observable from this repository. Whether all redundant unique indexes from D-1 are actually present, whether the `NO ACTION` foreign keys from D-4 are live, and the effective `PRAGMA foreign_keys` value in production all need a direct check against the production database before any migration.
- The local foreign-key and transaction reproductions used `@libsql/client` 0.14.0 against a local `file:` database (native libsql). The remote Turso Hrana path was not exercised; its default foreign-key behavior and transaction concurrency may differ.
- The exact `turso` CLI subcommands in D-3 (`db dump`, `db create --from-db`, `db shell`) should be confirmed against the installed CLI version.
- It is not known whether production is migrated with `drizzle-kit migrate` or `push`; the risk profile of D-1 and D-3 depends on this.
- The `migrations/migrations.sqlite3` file is zero bytes and carries no applied-migration history, so it provides no evidence about what actually ran.
